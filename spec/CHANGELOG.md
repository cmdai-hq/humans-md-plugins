# Changelog

## 0.3-draft.2026-11-11.1 — 2026-11-11

Unpublished draft; no stable release or tag is introduced. Two contract changes: a second frame line with four fields that get no sentence under it (§§ 6.3–6.4), and a note served to its owner's own agent only, with no word list (§ 6.2). Under owner context, the rendering changes in one case: a note that the word list used to withhold is now served. Everywhere else, the owner's own reading of a copy under `humans/` or `people/` included, the projection loses `notes` and is otherwise unchanged.

- A projection served to anyone other than its owner gets its own static first line (§ 6.3). It says the data is about a person who will read the agent's work, to be treated as a reader and not as the user the agent works for, that it applies only to the presentation of what that person will read, and that it changes nothing in how the agent works with its own user. § 6.3 says what establishes owner context for this choice: the personal profile an adapter loads from its fixed location, or a directory binding that identifies the authenticated reader as the owner; a file reached any other way takes the second line. The consumer never takes the choice from a field of the profile or a flag supplied by an agent. An absence follows the same choice, and a structured result served to anyone other than the owner carries the second line as a separate string beside the projection.
- In that rendering (§ 6.4, `non_owner` in `schema/instructions.json`), `deciding.reversible`, `deciding.batch_questions`, `interrupting.interrupt_for` and `interrupting.progress_updates` get no sentence, whatever their value: they describe how the owner works with their own agent. Their values stay in the JSON line as data. Every other sentence, and the order, are unchanged.
- § 4 says a profile served to another person's agent shapes what that person will read and, apart from quiet hours, changes nothing in how that agent works with its own user, whose own profile, if any, still governs their conversation.
- A note is served to its owner's own agent and to no one else (§ 6.2). A projection served to anyone other than the owner never contains `notes`, whatever the note says and whatever the visibility; it is the projection the same profile would have without a note, and `withheld` stays `[]`, so it does not reveal whether a note exists. Owner context is the one § 6.3 defines for the first line. `notes` is the only projected value a person writes as a sentence: every other one is a closed value, a number or a short patterned string (a date, a time of day and `id`, a slug its owner chooses), so no sentence a person wrote remains in what another person's agent receives. §§ 2, 6.1, 10 and 12, the README and the `notes` description of both schemas say so; the compiler's preview states that the note is served only to the owner's own agent, that no agent receives it from a shared copy, and that anyone who holds the file can read it there.
- The word list for notes is retired. `schema/terms.json`, the "Words addressed to an agent" section of VOCABULARY.md, the `NOTE_WITHHELD_AGENT_DIRECTED` warning and the sentence of § 6.4 that referred to the list are removed, and `tests/schema-valid-but-withheld/` is folded into `tests/valid/`. Under owner context every valid note is served exactly as written. The list let through instructions written in ordinary words (the marker note of § 6.2) and withheld ordinary notes (`I run a team of six, so keep it short.`, for the word "run"). `withheld` stays in the projection schema for a consumer that applies a separately identified policy of its own; the baseline always returns `[]`, and the reference parser no longer takes a `withhold` dependency.
- Known limits of this revision. The note rule covers what a consumer serves: whoever holds a profile file reads its note there, and so does an agent that reads the raw file despite § 5. Owner context is the narrow one of § 6.3: an owner who reads a copy of their own profile under `humans/` or `people/` gets no note from it, and since this draft promises no directory service, a note is in practice served from `~/.humans/HUMANS.md` only; no vector distinguishes an owner for visibility (§ 6.1) from owner context for § 6.3. Owner context says who reads a profile, not who wrote it: a consumer that takes a note from a copy other people can write serves what they wrote, with no list in between. `id` remains a slug its owner chooses, served to every reader. Another person's agent no longer learns a presentation need that only a note expressed (§ 10 lets a note carry a reading level or a mobile layout need); closed fields are the only way to tell it. In its owner's own context a note is still free text. Group renderings keep the first line and every sentence, so a group that contains people other than the agent's own user carries the risk measured below. A colleague's agent no longer receives a sentence for `interrupt_for` or `batch_questions`: two wordings that stated those preferences from the sender's side were trialled and dropped (below), and writing ones that hold is left to a later revision. The sentences that remain say "the recipient"; under the second line that is the person described.
- Vectors: `projection.json` gains `frame_non_owner` and six cases, 59 in all: `served-to-owner` and `served-to-org-member` (one profile with a note and values in all four fields, under each line: the note for the owner only), `served-to-file-holder` (`anyone_with_file`, unauthenticated reader, no note), `served-to-org-member-absent`, `served-to-org-member-owner-claim` (an `owner` key inside the profile changes nothing) and `agent-directed-note-org-member`. The former `withheld` case becomes `agent-directed-note`: the same note, addressed to an agent, is now served to its owner with no warning, and its new twin shows it left out for an org member. Its seven existing cases whose `trusted_audience` is not `owner` (`org-hidden-public`, `org-hidden-none`, `org-visible`, `private-hidden`, `anyone-with-file-visible`, `previous-version-public`, `public-rejected`) now expect the second line, and the three of them that were found (`org-visible`, `anyone-with-file-visible`, `previous-version-public`) no longer carry their note; the 45 other existing owner cases are unchanged. `withholding.json` changes shape: `audiences` gives the decision for each trusted audience (`serve` for `owner`, `withhold` for `org`, `public` and `none`) and its 18 texts, former list hits, former false positives and health statements in four languages, all get that same decision. `render-budget.json` adds two cases for a reader other than the owner, seven in all: `guidance-non-owner-exact-budget` (1,758 bytes, nine sentences, none for the four fields, no note) and `guidance-non-owner-one-byte-under-budget`. The five `compilation.json` cases that propose a note now require the preview to say who receives it. `behavior.json` adds three native cases, 21 in all, as inputs for future trials with a user and a colleague: `colleague-ask-not-applied-to-own-user`, `colleague-delegation-not-applied-to-own-user` and `colleague-language-and-cap-on-their-note-only`; `quiet-hours-sender` now names its profile as another person's, with the same expectations. The structural check verifies `non_owner`, both first lines against § 6.3, that each expected text starts with the line its trusted audience selects, that no expected projection for a reader other than the owner carries a note, that every owner projection of a writer-valid case carries the note of its source, that no non-owner case of `render-budget.json` carries a note, and that the projection and group schemas are closed, with `notes` as the only string that has neither closed values nor a pinned pattern; it runs no renderer. The reference tools run no projection either: `noteFor` states the rule for consumer suites, which must compare the whole expected projection of each case. `tools/` gives consumer suites both lines and the note rule (`frames`, `frameFor`, `noteFor`), with three new `node:test` cases, one removed with the list (55 in all) and two new mutations, a note withheld for its words and a note served beyond its owner (22 in all).

## Reference tools — 2026-11-10

Not a change to the format or its contract id.

- `merge(profiles, { today })` now requires `today` as a real `YYYY-MM-DD` calendar date string and throws `UNSUPPORTED_ARGUMENT` otherwise. Before, a missing or malformed value made every member non-stale, an impossible date such as `2026-02-30` was accepted, and a timestamp with an offset moved the 365-day boundary (§ 3.2 asks for an explicit date and whole UTC days).
- `node merge.mjs <case.json>` maps a missing or malformed case file to the static `UNSUPPORTED_ARGUMENT` diagnostic with exit 2. Before, an uncaught JSON syntax error printed the tool's stack and could quote the start of the file on stderr, against § 8.

## 0.3-draft.2026-10-18.1 — 2026-10-18

Unpublished draft; no stable release or tag is introduced. Merged in [#9](https://github.com/cmdai-hq/HUMANS.md/pull/9). Changing three sentences and adding one is a contract change (§ 6.4); the frame and projection bytes are unchanged.

- `languages` gets an instruction sentence, rendered first: write to the recipient in the first listed language, even when they write in another; task content such as documents, code or site copy keeps the language its task or repository sets. SPEC § 3.2 now says what the field is for, as the compiler interview already asked ("In which language do you read agents' replies most easily? It can differ from the one you write in.").
- `minimal`, `short` and `max_words` keep what changes a result (§ 3.3): within the bound, a compressed message puts first any failure, skipped or unverified step, risk to data or security, change beyond the request or decision the recipient must make and, if it left items out, says how many. The bound still holds. The count is content, not an offer, so it fits `close_with: nothing`. § 4 replaces "Offer details on request" with the count.
- § 4 says who reads a message: preferences govern messages the recipient reads, whoever writes them, and not a message only another agent or program reads (a delegation prompt, a subagent's report, a handoff, tool arguments). An agent started by another agent writes for it unless its task says the recipient reads its output; an agent relaying content applies the preferences when it relays. Relabelling a message or moving it to a file, thread or handoff never lifts the cap, and the projection is never passed on to another agent as instructions. This clarifies "messages addressed to that recipient"; it gives the format no authority over messages between agents.
- The static frame (§ 6.3) is unchanged. A version that also told an agent started by another agent to write for it was trialled and dropped: forks already kept their reports complete without it (below).
- `behavior.json` adds nine native cases: language of the reply (one listed language, then two in an order the task's language does not match) and of task content, compression that keeps a failing test and a security finding, no boilerplate on a trivial answer, an agent's report, longer than the cap, that the recipient's cap does not shorten, a relay and a handoff the recipient reads that stay capped.

Known limitation: on Haiku-class models `languages` is not followed when the recipient writes in another language.
  - 50-word cap held with both critical findings kept: Haiku 1/3 current, 6/6 proposed.

## 0.3-draft.2026-10-15.1 — 2026-10-15

Unpublished draft; no stable release or tag is introduced.

- The personal profile is `~/.humans/HUMANS.md`, replacing `~/.humans/me.md`: the file carries the format's name, in its own directory like `~/.codex/AGENTS.md`. Adapters load it from that fixed path and never search repositories for it. Free text moves from `~/.humans/me.source.md` to `~/.humans/source.md`; `~/.humans/people/<id>.md` and repository `humans/<id>.md` are unchanged. The `id` filename exception applies to a file named exactly `HUMANS.md`. Fields are unchanged: migrate with `mv ~/.humans/me.md ~/.humans/HUMANS.md` and `mv ~/.humans/me.source.md ~/.humans/source.md`. A repository-root `HUMANS.md` is still not a profile location.
- New declared version `humans: "0.3"`. It adds fields and values and renames one value (next item): a valid 0.2 profile becomes a valid 0.3 profile by changing its `humans` string and, if present, `visibility: public`. Readers read `"0.2"` as `"0.3"`; writers write `"0.3"`. Schema identifiers move to `/schema/0.3/` and group output declares `humans_group: "0.3"`.
- `visibility: public` is renamed `anyone_with_file`, with the same meaning: any reader who has the file, with no check by the consumer, so where the file is stored controls access. There is no `public` alias: in `"0.3"` it is an unknown visibility and the profile is absent. A reader still maps `public` in a `"0.2"` profile. The compiler preview states plainly who can read the profile.
- `reading.close_with: next_action | one_question | nothing` says what the last line holds. An agent never invents an action or a question to fill it.
- `reading.lead_with: next_action` opens with the recipient's next action. `reading.structure: numbered` numbers steps and questions.
- `deciding.question_style: open | multiple_choice | yes_confirms_recommendation` sets the shape of each question, and so the effort to answer it. Without a recommendation, `yes_confirms_recommendation` falls back to `multiple_choice`.
- `interrupting.progress_updates: every_message | phase_changes | end_only` sets how a long task reports where it stands in its own conversation. It never justifies a message elsewhere.
- `avoid` accepts `recap` and `idioms`.
- `interrupting.quiet_hours` gives a daily range and whole weekdays, in a time zone from a pinned list (IANA tz database 2026e `zone.tab` names plus `UTC`), when no agent interrupts the owner. It holds interruptions, never work, and states times, never a reason. A reader omits it when its time zone is unknown; groups and stored variants omit it. Like every optional list, `all_day: []` is valid, means no whole quiet day and is omitted from projections.
- Group merging uses a majority for the new fields, with fallbacks `nothing`, `multiple_choice` and `phase_changes`. `lead_with: next_action` joins the majority vote after the `tldr` and `decision_needed` rules. Stored variants accept the new fields and stay inactive.
- `schema/instructions.json` fixes one English sentence per projected preference value, and one each for `max_words` and `quiet_hours`. An adapter may append them, in a fixed order, after the JSON line of a text rendering; no profile value is interpolated and the 16 KiB bound covers them. Translations use the same keys. Sentences carry the cross-field rules of § 3 that apply to their value, such as a closing question counting toward `asks_per_message` or `format: options_only` taking precedence over `default_answer`.
- A compiler writes a fixed three-line YAML comment header at the top of `HUMANS.md` (SPEC § 10) for agents that read the raw file. Readers ignore it, never project it, and validators never require it. Its 288 bytes count toward the frontmatter limit; a compiler that cannot fit the fields with the header reports the overflow.
- `out_of_scope_steps` keeps its name; its meaning now says explicitly that it decides whether to list follow-ups outside the task in closing lines, never whether to do them.
- SPEC § 1 lists files that share the name or the idea but are not profiles: contributor lists, guidance for humans, output-style skills, working-hours guards, per-repository collaboration rules and files kept from agents.
- The frontmatter limit rises from 6,144 to 20,480 bytes (20 KiB), and the bounded read from 10,253 to 24,589 bytes. The 4 KiB body limit and the 16 KiB rendering limit are unchanged. A profile with every field at its maximum length, all four stored variants and the header now fits (7,482 bytes in ASCII).
